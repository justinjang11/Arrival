TASK: Build Arrival’s account-creation and initial profile-setup interface using temporary, nonpersistent development state.

This task creates a testable frontend flow. It does not create real accounts, connect a database, or implement real authentication.

1. Create a dedicated setup route.

Create the account-creation and profile-setup experience at:

`/setup`

Keep the existing placeholder landing screen unchanged. The completion report must clearly explain how to open `/setup` in the Replit preview.

Do not add a production navigation system.

2. Build a short, structured setup flow.

The complete flow must be designed to take no more than three minutes and should use a small number of logically grouped steps.

At minimum, include:

* account credentials;
* delivery information;
* product-pool preference;
* sizing and fit-reference information;
* review or submission behavior.

Use a visible progress indicator so the user understands where they are in the process.

Allow the user to move backward without losing information entered during the current browser session.

Do not build Wishbone in this task.

3. Implement every account and profile field required by the product specification.

This includes, as applicable in the specification:

* email;
* password;
* full name;
* phone number;
* shipping address;
* address line 2 as an optional field;
* Menswear, Womenswear, or Both;
* height;
* weight;
* reference brand and reference size;
* top sizing;
* bottom sizing;
* shoe sizing.

Read the specification for the exact required address fields, sizing fields, labels, and acceptance criteria. If this prompt’s summary differs from the specification, the specification controls.

Product-pool preference must not be described as the user’s gender or gender identity. Use language such as “Which products should Arrival shop?”

Do not request or display payment information.

4. Include the required delivery explanation.

Display this helper copy near the delivery fields:

“Used to prepare retailer checkouts. Arrival never completes a purchase without your review.”

Do not imply that Arrival purchases products automatically.

5. Add deterministic form validation.

Required fields must prevent progression or completion when empty or invalid.

Validation must:

* identify the specific field requiring correction;
* display errors in clear language;
* associate each error with its field;
* preserve valid information when another field fails;
* permit address line 2 to remain empty;
* require a valid phone number and required shipping-address fields before setup can complete;
* avoid inventing a permanent product policy where the specification is silent.

Use simple, deterministic prototype validation. The same entry must always produce the same validation result.

If the specification does not define a final password policy, do not invent or present one as permanent. Require a nonempty password for this prototype, label that behavior as a temporary development assumption in code comments and tests, and report it at completion.

If units, allowed size formats, international-address behavior, or another validation detail remain unspecified, use the least restrictive workable prototype behavior. Isolate and clearly document every such temporary assumption rather than recording it as a product decision.

6. Keep credentials separate from profile information.

Define clear TypeScript structures for:

* temporary account credentials;
* the editable profile/setup information;
* validation errors;
* the setup step or flow state.

Do not place the password inside the completed profile object.

Do not print, log, save, or display the entered password after submission.

7. Use temporary, nonpersistent state only.

Form information may exist in React state while the setup page is open.

Do not store form information in:

* Supabase;
* another database;
* `localStorage`;
* `sessionStorage`;
* cookies;
* files;
* URL parameters;
* logs;
* analytics;
* an external service.

Refreshing or closing the page may erase the entered information. Clearly identify this as temporary development behavior in code comments and the completion report.

Tests must use clearly fictional information. Do not enter or embed real names, addresses, phone numbers, emails, or passwords.

8. End at the correct milestone boundary.

After valid submission, show a brief, friendly confirmation that the profile setup portion is complete. The exact wording is not prescribed.

Do not claim that the entire onboarding process is complete because Wishbone has not been built.

Do not:

* build Wishbone rounds;
* reveal the final Saved Outfits / Home / Account navigation;
* open the final Home experience;
* generate recommendations;
* create an Account editing screen;
* create checkout behavior.

Structure the profile form logic so it can be reused by a future Account editing screen, but do not build that screen now.

9. Keep the visual design deliberately restrained.

Create a clean, usable, responsive interface using the project’s existing styling system.

Include:

* properly associated field labels;
* keyboard-operable controls;
* readable error messages;
* visible focus states;
* appropriate input types;
* a clear primary action;
* Back and Continue behavior where applicable.

Do not attempt to finalize Arrival’s brand identity.

Do not add:

* external images;
* remote fonts;
* animations requiring a new package;
* a component library;
* design-system dependencies;
* elaborate illustrations;
* final marketing copy.

10. Add focused automated tests.

Add component and validation tests covering at minimum:

* the setup route renders;
* required fields prevent premature progression;
* an invalid email displays a clear error;
* a missing password prevents progression;
* address line 2 is optional;
* missing or invalid phone information prevents completion;
* required shipping-address information prevents completion when missing;
* Menswear, Womenswear, and Both are represented as product-pool choices;
* entered information remains intact when moving backward and forward;
* valid fictional information can complete the setup flow;
* the completion state does not reveal the final main navigation;
* the password is excluded from the completed profile information;
* no browser-storage API is used.

Use fixed fictional values so the tests are deterministic.

Do not weaken or remove existing tests.

Do not modify:

Do not add new npm packages. Use the packages already installed in the repository.

The task should not require changing `package.json` or `package-lock.json`.

If either file changes unexpectedly, investigate and explain why. Before finishing, confirm that `package-lock.json` contains zero occurrences of:

`package-firewall.replit.local`

Do not rewrite dependency versions merely to regenerate the lockfile.
